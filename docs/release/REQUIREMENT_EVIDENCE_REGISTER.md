## Purpose and interpretation

This is a working evidence register for all 64 approved requirement IDs. It maps likely implementation areas and existing test-file candidates to each requirement. These are **discovery leads**, not proof that the cited code implements the requirement or that a test verifies the full requirement.

Every row starts at `NOT RUN` for **requirement-level acceptance** because the existing CI result is not yet mapped to a specific requirement and its acceptance criteria. Do not promote a row to `PASS` based on file existence, a passing aggregate test suite, or a test whose assertion scope has not been reviewed.

## Controlled evidence outcomes

- `PASS`: acceptance criteria passed on a named revision with retained evidence.
- `FAIL`: tested behavior violates acceptance criteria.
- `BLOCKED`: verification cannot be completed because of a documented blocker.
- `SKIPPED`: an explicitly approved, justified exclusion from a particular verification run; does not satisfy a mandatory release gate.
- `NOT RUN`: no adequate requirement-specific execution evidence has been recorded.

Requirement lifecycle statuses (`APPROVED`, `IMPLEMENTED`, `DEFERRED`, etc.) are separate from these evidence outcomes.

## Evidence needed to close a row

For each requirement, review the actual acceptance language, inspect the implementation, verify that the candidate test asserts the required behavior including negative/boundary cases, execute the test or workflow against a fixed commit, and attach the command/run URL plus relevant result. Where the existing test suite is insufficient, record a gap and add a test rather than assuming coverage.

The current main branch has release-gate, Command Center vertical-slice, and training-provenance test suites. These are useful starting points, but the register does not claim a full native release, export/inference, clean ZIP install, or production convergence run has passed.

## Release-level known gaps

These remain separate hard gates and must not be closed by the register's existence:

- Native llama.cpp bootstrap and native inference on the intended release environment.
- GGUF export, quantization where supported, export manifest integrity, and optional Ollama verification.
- Complete browser Command Center operator workflow against real backend/run state, beyond API vertical slices.
- Clean-machine installation and ZIP-download acceptance, including no undeclared cache or local state.
- End-to-end provenance from source acquisition through cleaning, deduplication, weighting, tokenizer, shards, checkpoint, and export.
- Training/evaluation evidence sufficient to support any convergence, quality, performance, or compatibility claim.
- Exact candidate revision/package identity and retained release report.

## Update protocol

1. Freeze the tested source revision and package identity.
2. Review and refine each candidate implementation/test mapping against the requirement's exact acceptance language.
3. Run targeted positive, negative, and boundary tests; record evidence URLs and result hashes where available.
4. Record each gap, failure, blocker, or approved skip without changing its meaning to improve aggregate status.
5. Recompute the release decision from mandatory requirement outcomes. Any mandatory `FAIL`, `BLOCKED`, or `NOT RUN` keeps certification at NO-GO.
